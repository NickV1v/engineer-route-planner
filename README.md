# Выезд — планирование маршрутов инженеров

Веб-приложение для диспетчера выездной службы: распределяет заявки между инженерами, строит маршруты с учётом транспорта и рабочих смен, показывает расписание и помогает перепланировать день при изменениях.

В основе — FastAPI, собственный оптимизатор C++20 и интерфейс React/TypeScript. Результат каждого расчёта проходит независимую проверку ограничений.

## Возможности

- **Планирование из CSV.** Загрузка заявок и сотрудников, проверка ошибок по строкам, настройка навыков, транспорта и смен.
- **Автоматическое распределение.** Учёт квалификации, клиентских окон, времени поездок, доступного транспорта и выданного оборудования. Неназначенные заявки показываются с объяснениями.
- **Карта и таймлайн.** Маршруты, последовательность визитов, работа, переезды и ожидание. Можно отдельно показывать и скрывать каждого инженера.
- **Разные виды транспорта.** Автомобиль, велосипед, ходьба и общественный транспорт с пешими подходами, метро, пересадками и выходом к адресу.
- **Уточнение адресов.** Поиск адреса, выбор точки на карте и ручное исправление координат до начала расчёта.
- **Перепланирование.** Новая срочная заявка, отмена работы или недоступность инженера. Изменения сначала показываются как предложение и применяются после принятия диспетчером.
- **История и экспорт.** Сохранение принятых планов, Excel, печатные маршрутные листы и полный JSON со сценарием и матрицами.

## Интерфейс

### Маршруты и расписание в одном представлении

Цвет связывает маршрут на карте с работами инженера на таймлайне. Номера обозначают порядок визитов; светлые участки расписания показывают поездки и ожидание. На скриншоте включены только **три маршрута**, остальные скрыты кнопками с глазом — исходный план при этом не меняется.

![Три маршрута инженеров и соответствующие им визиты на таймлайне](assets/screenshots/day-plan.png)

### Подробный переезд на общественном транспорте

Выбор поездки показывает её геометрию и состав: пеший подход, ожидание, линии метро и пересадку. На скриншоте открыт **один инженер** и выделен переезд с линиями 15 и 11. Длительность и расстояние относятся к конкретному примеру, а не к гарантированному времени поездки.

![Выделенный переезд одного инженера: пеший подход, ожидание и пересадка между линиями метро](assets/screenshots/metro-trip.png)

Скриншоты сделаны на синтетическом наборе. Подпись карты свёрнута штатной кнопкой ⓘ. Источники картографических данных: OpenStreetMap contributors, OpenFreeMap и OpenMapTiles; адресные данные — OpenStreetMap и DaData.

## Локальный запуск

### Требования

- Python 3.12 или новее;
- Node.js 22.12 или новее и npm;
- Make и компилятор с поддержкой C++20;
- для реальной маршрутизации — дополнительные зависимости и подготовленные графы.

Команды ниже рассчитаны на Unix-совместимую оболочку. Выполняйте их из корня репозитория.

```bash
git clone https://github.com/NickV1v/engineer-route-planner.git
cd engineer-route-planner

python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
python -m pip install -e . --no-deps

make solver
npm --prefix frontend ci
npm --prefix frontend run build

python -m uvicorn dispatch.api:app --host 127.0.0.1 --port 8000
```

Откройте **http://127.0.0.1:8000**. Интерактивная документация API доступна по адресу **http://127.0.0.1:8000/docs**.

**Запуск интерфейса и готовность к расчёту — разные этапы.** Исходные таблицы и тяжёлые транспортные графы в репозиторий не включены:

| Локальные данные | Для чего нужны |
| --- | --- |
| `Нормативы.xlsx` в корне | Загрузка заявок и нормативы длительности работ |
| `Обезличивание.zip` в корне | Прежний CLI, встроенные сценарии API и часть интеграционных тестов |
| Дорожные и транспортные графы | Расчёт реальных переездов; пути задаются в `config/routing.json` |

Без этих данных полноценный расчёт после клонирования недоступен. Локальные данные не следует добавлять в Git.

### Проверка без исходных архивов и городской сети

В репозитории есть небольшой вымышленный транспортный граф. Он позволяет проверить поиск пути с метро и автобусом без таблицы нормативов, исходного архива и внешних API:

```bash
python -m pip install -r requirements-routing.lock
python -m dispatch.routing transit \
  --network tests/fixtures/transit_network.json \
  --origin office --target A
```

Ожидаемый результат: **2040 секунд и 9550 метров**, включая пешие участки и ожидание. Это ручной тестовый пример, а не маршрут по действующей городской сети.

### Подготовка реальной маршрутизации

Дорожные поездки рассчитываются локально через Valhalla по данным OSM. Для общественного транспорта используется отдельный граф линий и пересадок. Установите зависимости подготовки:

```bash
python -m pip install -r requirements-routing.lock
python -m pip install -e '.[routing-import]'
```

Подготовка выполняется последовательно. Аргументы каждого скрипта доступны через `--help`.

| Скрипт | Назначение |
| --- | --- |
| [build_routing_graph.py](scripts/build_routing_graph.py) | Сборка дорожного графа из `.osm.pbf`; `--bicycle-dismount` создаёт отдельный граф велосипеда со спешиванием |
| [extract_transit_osm.py](scripts/extract_transit_osm.py) | Извлечение транспортных объектов из OSM |
| [export_rail_osm.py](scripts/export_rail_osm.py) | Проверка и экспорт рельсовой сети; требует внешнего валидатора Organic Maps subways и справочника городов |
| [build_transit_network.py](scripts/build_transit_network.py) | Объединение рельсовой сети, автобусных и трамвайных линий |
| [connect_transit_walks.py](scripts/connect_transit_walks.py) | Добавление пеших переходов по дорожной сети |

Для рельсового валидатора закреплена ревизия `2329b6aa8be4864d2dfa10073c7fd0756e83bb03`; его каталог должен называться `subways-2329b6aa8be4864d2dfa10073c7fd0756e83bb03`. Валидатор и его справочник поставляются отдельно. Сборщик рельсовой сети настроен на Москву.

Готовые каталоги укажите в [config/routing.json](config/routing.json). Скрипты создают новые каталоги результатов: существующие графы не перезаписываются. Подготовка большой территории требует заметного времени и дискового пространства; это отдельный шаг, а не часть старта API.

Для проверки интерфейса без реальных графов можно явно включить тестовый режим:

```bash
DISPATCH_ROUTING_MODE=synthetic python -m uvicorn dispatch.api:app \
  --host 127.0.0.1 --port 8000
```

Он использует искусственные матрицы и не заменяет реальную маршрутизацию. Требование к таблице нормативов для загрузки заявок сохраняется.

## Как пользоваться

1. На вкладке **«План»** загрузите CSV заявок и CSV инженеров. Проверьте оба файла.
2. В **«Настроить инженеров»** проверьте навыки, транспорт и смены; исключите недоступных сотрудников.
3. Нажмите **«Рассчитать план»**. Если адреса неоднозначны, уточните координаты или исключите соответствующие заявки и продолжите расчёт.
4. Изучите маршруты, таймлайн и метрики. Нажмите имя инженера для подробного маршрута, а заявку — для её карточки. Для читаемости карты оставьте видимыми несколько маршрутов.
5. При изменении дня создайте срочную заявку, отмените работу или отметьте инженера недоступным. Просмотрите предложение перепланирования и примите либо отклоните его.
6. Через **«Экспорт плана»** скачайте результат. Excel и печатные листы поддерживают выбор видимых маршрутов.

Все инженеры начинают маршрут из общего офиса участка. После первого расчёта состав смены фиксируется; сотрудники вне него автоматически не привлекаются. Уже начатые визиты и принятые обязательства сохраняются при перепланировании.

## Входные данные

Примеры синтетических заявок: [Восток](data/samples/Восток.csv), [Юго-восток](data/samples/Юго-восток.csv), [Югоцентр](data/samples/Югоцентр.csv). Состав команды: [Инженеры.csv](data/samples/engineers/Инженеры.csv). Генерация состава в конфигурации использует seed `20260917`. Каталоги `data/samples/invalid` и `data/samples/address-review` содержат примеры для проверки ошибок и уточнения адресов.

Поддерживаются UTF-8, UTF-8 с BOM и Windows-1251; разделители — точка с запятой, запятая или табуляция. Лимит каждого файла — 2 МБ; в одном дне до 100 заявок и до 30 инженеров.

### Заявки

| Поле | Содержание |
| --- | --- |
| `ID` / `Заявка` | Уникальный идентификатор |
| `Тип` / `Тип заявки BK` | Подключение, Дозаказ, Локальная заявка или Глобальная проблема |
| `Начало`, `Окончание` | Клиентское окно с датой, например `17.08.2026 10:00` |
| `Адрес` либо `Широта` и `Долгота` | Местоположение заявки; способы можно смешивать в одном файле |
| `Длительность, мин` | Необязательная длительность; при отсутствии берётся норматив |
| `Навык` | Необязательно: `installation`, `local`, `emergency` |
| `Требуемый транспорт` | Необязательное ограничение транспорта |

После заявок требуется одна строка офиса. Точный формат показан в файлах-примерах. Окно ограничивает **начало** работы, а вся работа с переездами должна укладываться в смену.

### Инженеры

Обязательные поля: `ID`, `Навыки`, `Транспорт`, `Начало смены`, `Конец смены`. Поле `Имя` необязательно. От одного до трёх навыков перечисляются через `|`. Транспорт: автомобиль, пешеход, велосипед или общественный транспорт. Отдельные стартовые адреса сотрудников не задаются.

## Как устроен расчёт

```text
CSV → проверка данных → уточнение координат → матрицы поездок
                                                ↓
                              baseline и C++-оптимизатор
                                                ↓
                                 независимая проверка
                                                ↓
                                сохранённый план в SQLite
                                                ↓
                                 карта, таймлайн, экспорт
```

Baseline последовательно назначает работы допустимым инженерам. Оптимизатор улучшает распределение в пределах заданного бюджета поиска. Приоритеты текущей политики: аварии, подключения, затем ремонт и дозаказы; далее учитываются состав смены и эффективность поездок. При перепланировании дополнительно учитывается стабильность принятых назначений. Глобальный математический оптимум не гарантируется.

Оба алгоритма используют одни входные данные и матрицы. Независимый checker проверяет допустимость результата. Предложение перепланирования применяется атомарно после принятия; отклонение сохраняет прежний план.

Кеш поездок живёт **только в пределах одного расчёта**. Архивы нужны для истории, а не для ускорения следующего запуска. Исправление координат не переписывает географию и матрицы уже сохранённого дня.

## Структура проекта

| Каталог | Содержание |
| --- | --- |
| `dispatch/` | API, импорт, baseline, независимая проверка, события, экспорт и SQLite |
| `dispatch/routing/` | Дорожная и транспортная маршрутизация, геометрия, матрицы |
| `solver/` | Оптимизатор C++20 и ядро поиска общественного транспорта |
| `frontend/src/` | Интерфейс React/TypeScript, Leaflet и векторная карта |
| `config/` | Параметры сценария и пути локальных транспортных данных |
| `scripts/` | Подготовка графов и проверки маршрутизации |
| `tests/`, `frontend/tests/` | Backend- и браузерные тесты, небольшие фикстуры |
| `data/samples/` | Синтетические CSV-примеры |

## Разработка и проверки

Для разработки запустите backend и Vite в разных терминалах:

```bash
python -m uvicorn dispatch.api:app --reload --host 127.0.0.1 --port 8000
```

```bash
npm --prefix frontend run dev
```

Vite открывается на http://127.0.0.1:5173 и проксирует `/api` на локальный backend.

```bash
make test
python -m ruff check dispatch tests
python -m ruff format --check dispatch tests
npm --prefix frontend run build
(cd frontend && npx playwright install chromium)
npm --prefix frontend run test:e2e
```

При установленном Google Chrome браузерные тесты можно запускать через `PLAYWRIGHT_CHANNEL=chrome npm --prefix frontend run test:e2e`. Интеграционные тесты требуют локальных `Нормативы.xlsx` и `Обезличивание.zip`; без них весь набор тестов не пройдёт. Тесты не вызывают живые картографические API.

## Настройки и ограничения

| Переменная окружения | Назначение |
| --- | --- |
| `DISPATCH_ROUTING_MODE` | `real` по умолчанию; `synthetic` для тестовых матриц |
| `DISPATCH_STORAGE_PATH` | Путь к базе планов; по умолчанию `artifacts/dispatch.sqlite` |
| `DISPATCH_PHOTON_URL` | Адрес сервиса геокодирования Photon |
| `DADATA_API_KEY` | Необязательные интерактивные подсказки и уточнение адресов через DaData |

Ключи передавайте локально через окружение или `.env.local`, не добавляя их в репозиторий. Отсутствие ключа DaData не отключает всю обработку адресов: доступны локальный справочник, координаты и Photon.

- Время поездок оценочное: нет пробок, точных отправлений транспорта и оперативных закрытий.
- Покрытие маршрутов зависит от подготовленной выгрузки OSM и качества транспортных связей.
- Карта и внешнее геокодирование требуют сети; основные дорожные расчёты выполняются локально.
- Статусы в плане описывают назначения и расписание, а не подтверждённое фактическое выполнение работ.
- Это прототип для демонстрации и локальной работы; пользовательская авторизация не реализована.
